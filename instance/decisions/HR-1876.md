## What was answered, and it was "nothing"

Asked what is planned for this, the honest answer at the time of writing was: nothing,
beyond row V3-1.6, filed minutes earlier, recording that v3 has no lane launcher at all.

## The measured obstacle

v3 does not merely lack this — it **structurally forbids** it.

`core/schema.ts`:

```
createManager(input: { id; missionId; parentId; depth }): void {
  if (input.depth !== 1 || input.parentId !== input.missionId)
    throw new SchemaError("manager parent/depth must be mission/1");

createLane(...):
  if (input.parentId !== input.managerId)
    throw new SchemaError("lane parent must be its manager");
```

So the tree is fixed at mission(0) → manager(1) → lane(2), a lane's parent must be its
manager, and **a lane cannot have lane children**. Under the operator's model a
second-level agent both does work and spawns third-level juniors; today a lane can only
be a leaf. The three levels that exist are not the three levels he is describing.

`instructions/roles.md` also says the manager is optional and does not bound the fleet
("A manager, when used, owns one bounded mission and one terminal rollup. The flat
coder-lane fleet remains bounded by capacity policy, not by a manager"), which matches
his sense that the manager layer was set aside.

And none of it runs: the only mechanism that actually starts an agent session,
`orchestrator/fleet/launch-lane.sh`, exists solely on `v2-deprecated`. Every lane
dispatched on 2026-08-03 was launched from that v2 working tree. Structure without an
executor — the repository's dominant defect shape — at the level of the whole agent
model.

## What this record does not decide

Whether the second level is modelled as today's `manager` row, as a `lane` permitted to
parent lanes, or as something else, is a design decision that needs the operator's
restated model first. Recording the obstacle is not the same as choosing the fix, and
choosing it before he restates the model would repeat exactly the failure this file
exists to correct.
