## The decision

1. **Top orchestrator = Codex `gpt-5.6-sol`** (reasoning effort high), not a
   resting Claude tier. `top_provider: codex`.
2. **Claude is reserved entirely** — not spent on routing at all.
3. **Connector work runs as short-lived Claude errand-agents** (Sonnet): spawn,
   fetch from Drive/Gmail, return, exit.
4. Fable stays escalation-only; lanes stay on Codex.

## Why the orchestrator's HR-269 position was wrong, and conceded

HR-269 argued for resting the top orchestrator on Sonnet and keeping a Codex top
as a mere armed fallback, on the ground that a Codex orchestrator would lose the
claude.ai MCP connectors (Google Drive, Gmail).

**That objection was tested and it failed.** `claude mcp list` from a clean CLI
invocation on this box returns Slack, Google Calendar, HubSpot, Intuit
QuickBooks, Gmail and Google Drive all `✔ Connected`. The connectors are bound to
the **account on this host**, not to any one session — so any Claude session
spawned here inherits them, and Vova's errand-agent design works exactly as he
described it.

With the objection gone his trade is better on both axes: a **strong** model on
**abundant** quota, versus the orchestrator's proposal of a weak model on scarce
quota. "Resting = cheapest model" was the wrong instinct — it optimized the wrong
variable. Conceded without reservation.

He also noted, correctly, that routing all lanes to Codex is something he has
asked for since day one; it was already binding in `vendor-routing.md` and simply
was not applied. Accepted without excuse.

## Residual unknown — do not report this as settled

`claude mcp list` proves the connectors resolve for a CLI invocation on this box.
It does **not** prove they resolve inside a **headless `systemd-run` lane**,
which is a different launch mode — and the old orchestrator's A4 notes warned
that interactively-authenticated MCP servers may be absent in headless/cron runs.
Verify on the first errand-agent actually spawned, and record the result here.
Until then the errand-agent path is proven for the CLI shape only.

## Consequence for NI-2 (Google Drive service account)

**REVERSED by Vova the same hour (Telegram 279) — NI-2 is GO, not parked.** His
words:

> Слухай, ті конектори, за які ти кажеш, то якісь конектори, які не дуже універсальні. Вони сильно підв'язані саме під Claude.Ми тобі для цього зараз і робимо service account, щоб ти міг нормально ходити туди, незалежно від того, на якому штучному інтелекті, на якому провайдері ти працюєш.

He is right and the orchestrator's advice to park it was wrong *given this very
decision*. The connectors are bound to the **Claude account**. Once the top
orchestrator is Codex, Drive access degrades to "spawn a Claude errand-agent to
go fetch it" — a dependency chain that should not be built on, and one that dies
entirely if the Claude account is ever unavailable. A service account is
provider-independent, which is the whole point of moving off Claude.

Superseded text (kept for the record): *"Weakened further. Gmail and QuickBooks
are connected too, so the debugging access NI-2 was written for already exists
without any credential. Keep NI-2 parked until an agent that genuinely cannot use
the account connectors needs Drive."*

Handling when the key arrives: he sends the JSON over Telegram and deletes the
message for everyone; the file is stored 0600 **outside** the repo; it is never
committed. Residual risk stated to him plainly — a Telegram-transported key must
be treated as exposed and is revocable in one click.
