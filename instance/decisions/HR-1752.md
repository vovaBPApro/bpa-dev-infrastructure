# HR-1752 — Explain the buttons in the message, not in the button

Verbatim (Vova, Telegram 1752, 2026-08-03):

> оці кнопки ти даєш, це класно, але пояснення кнопок треба давати в повідомленні,
> бо в кнопці я бачу тільки три слова максимум

## Rule

Inline-keyboard buttons are a **selection mechanism, not an explanation surface**. On
his client a label is legible only to roughly three words; anything longer is
truncated or unreadable. Therefore:

- Every option offered by `request_decision` must be described in the message body,
  labelled so the reader can map body text to button unambiguously (A/B/C, or the
  option's first word repeated).
- The button label carries only the shortest possible handle.
- A decision request whose options are only comprehensible by reading the button
  labels is a defect, even when the labels are technically accurate.

This interacts with the 5-line / ~600-character human-message ceiling
(`instructions/operator-feedback.md`, HR-302): the explanation must fit that budget
too. If the options cannot be explained inside the ceiling, the decision is framed too
wide — narrow it, or send the detail as an attached file and keep the question small.

The positive half of his feedback is recorded too: the buttons themselves are wanted
(«це класно»). This is a refinement of a mechanism he likes, not a request to stop
using it.

## v3 obligation

He asked explicitly that this go into the v3 plans as something to verify. So v3's
Telegram surface must treat button-label length as a checked constraint, not a
convention — a decision request whose options lack body-text explanations should be
caught by the transport layer, in the same way the message-length ceiling is enforced
today.
