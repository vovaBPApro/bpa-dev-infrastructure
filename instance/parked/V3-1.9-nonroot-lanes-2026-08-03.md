## What is now settled, and should not be re-litigated

**The design.** The v1 orchestrator, asked over the file channel, reported that its
production line never runs anything as root: one lingering non-root service user owns
the orchestrator, the daemon, the repository, the worktrees and the credentials. The
ownership handover, the `HOME` override and the `safe.directory` narrowing all cease
to exist rather than being solved. Quoted with its limits in
`instance/v3-nonroot-lane-model-2026-08-03.md`.

**Inter-lane confinement is out of scope, by evidence.** The v1 line does not have it
and says so. Round 3 disclaims it where a reader will find it
(`instructions/single-service-user.md:13-19`): a shared identity gives ownership
consistency, not security isolation. That is the honest position and it closed round
2's second blocker.

**`IPAddress*` is real, not decorative — proven by execution.** On this host's systemd
255 root user manager, a plain transient user unit reached a disposable HTTP server
(`exit=0`); the identical unit with `IPAddressDeny=localhost` /
`IPAddressAllow=127.0.0.53` timed out (`exit=28`). So the network boundary survives the
move to `--user` units. Caveat recorded by the reviewer: `systemd.resource-control(5)`
warns `IPAddress*` has no effect where cgroup/eBPF support is unavailable, and this was
measured on the **root** user manager only.

**The fail-closed paths hold.** Missing user, linger off, missing credentials, bad
owner/mode, non-root uid mismatch and a failed `setpriv` all terminate rather than
falling back to root (`orchestrator/fleet/launch-lane.sh:54-85`). Every artifact is
created **after** the `exec setpriv` at `:78-84`. Credentials stay at service-home
paths, require a regular readable file at mode 0600 owned by the service uid, and
`HOME` is not overridden in the user unit. Output reaches the log only through
`daemon/mask-stream.ts`; the fixture masked a credential-shaped value. Secret scan
clean, no credential copied into repository, prompt or log.

**A lane identity really can commit.** The fixture asserts effective uid **and** gid
and runs `git add` / `git commit` as `nobody` — real uid execution, not a mock
consuming flags. Note the fixture assigns the cloned repo and home to that same uid, so
it demonstrates the single-owner design and deliberately does **not** exercise a
root-owned parent repository.

**`bootstrap/provision-service-user.sh` is coherent standing alone**: root-only,
validates config and home, creates or validates the account, installs owned
directories, enables linger and verifies it, names interactive 0600 credential
locations without placing any credential. Its absence from `bootstrap/install.sh` was
an orchestrator decision to avoid colliding with the parallel stage-2 recut, and the
reviewer did not treat it as a defect.

## The lock the recut must satisfy

1. **Restore the deleted regression locks — this is first, and it is not optional.**
   `orchestrator/fleet/launch-lane.test.sh:97-126` now covers only absent user,
   credentials, linger and command file. Round 3 removed the locks for: atomic
   concurrent reservation, dangling-symlink refusal at **every** artifact location,
   failed-launch cleanup and name reuse, multi-element positional command, private
   `TMPDIR`, and the mask-stream path. Reading suggests the production behaviours
   survive (`orchestrator/fleet/launch-lane.sh:96-101,118-141,157-172`) — but the
   executable locks that proved them are gone, so the green suite is a **false green**
   for every launcher defect earlier rounds fixed. A row about privilege must not be
   the row that deletes evidence.
2. **Dispatch ordering must be provable.** Pack reservation, composition and prompt
   creation happen at `:125-149`, before `dispatch-lane.sh` at `:153`. Dispatch does
   precede the worktree, the lane `TMPDIR` and the transient unit, but **not every
   artifact** — which is what the mission claimed. The test uses `DISPATCH_OVERRIDE`
   (`:74-80`), observes a full-pack validation failure and still reports PASS, so it
   cannot serve as the fail-closed dispatch proof. Either make the claim true or state
   the real ordering and lock that.
3. **The installed-account evidence (V3-1.9a).** Everything about the production
   identity is reading plus fixture execution: the root→`bpa` re-exec, its user
   manager, credential ownership, a worktree commit, and the network filter under the
   identity production will use. None can be executed while the account does not exist.

## What the operator must decide

Provisioning is his call and nothing proceeds without it:

- create the service account and enable linger on this host;
- mint provider credentials by interactive login as that user (`codex login`,
  `claude`) — this is secret provisioning, CLAUDE.md rule 14;
- decide whether the **orchestrator itself** is de-privileged now or at the host
  cutover (V3-4.3). The v1 line runs the orchestrator as the service user; v3 runs it
  as root today, and the mechanism supports both.

Until then the fleet stays single-provider by constraint, and HR-1734 / V3-3.2 (a
cheap tier for mechanical lanes) stays blocked behind the same wall.
