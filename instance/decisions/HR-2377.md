# HR-2377 — Persist input and output token counts per model and per role

date: 2026-08-04

status: binding

## Ruling

1. **Count and persist token usage in the database**, not in a file and not in a status
   message: **input** and **output** counts, broken down by **model** and by **role**.
2. The stated purpose is graphs over time, so the store must be queryable by those
   dimensions and must survive restarts.
3. It follows the quota reading he asked for the same evening (HR-2367,
   `instance/quota-readings.tsv`): the percentage is the headline, the token counts are
   what explain it.

## Why this is the right measurement, and not merely a smaller one

The orchestrator told him hours earlier that it cannot read Claude quota itself —
`daemon/vendor-quota.ts` reads Codex from its JSONL but returns Claude as
`{ state: 'unknown' }`, so quota percentages depend on him sending a screenshot.

**Token counts do not have that problem.** They are observable at the point of use rather
than scraped from a vendor panel, so this is the part of consumption the machine can
actually own. His instruction therefore replaces an unmeasurable metric with a measurable
one, which is why it should be built rather than deferred behind the quota work.

Per model *and* per role is the load-bearing part. Cost arguments on this system are
currently about tiers — whether an escalated review round is worth it (HR-2166), whether
simple work belongs on a cheaper model (messages 1562, 1841, 2092, 2186), what a lane-hour
costs. None of those can be settled by a single total. A number that cannot be split by
model and role cannot answer any question he has actually asked.

## Constraint carried over

A model or role that reports nothing is recorded as **unmeasured, never as zero** — the
standing rule for this data, stated in workboard row V3-3.10 and in the header of
`instance/quota-readings.tsv`. This is destined for a graph, and a zero on a graph reads
as "we used nothing" rather than "we did not look".

## Where the work lives

Folded into **V3-3.10**, which already carries the persistence requirement, rather than
filed as a new row. V3-3.10's acceptance is extended: per-model and per-role input/output
token counts, persisted, surviving a restart, queryable for a time series.
