# HR-1680 — The orchestrator does not change its own model

Verbatim (Vova, Telegram 1680, 2026-08-03):

> а чого у оркестратора модель стала Luna low?????????? якого дідька? ти не маєш
> права сам міняти модель орка!" І переконавйся що нова інфраструктура цього не
> робитиме!

Captured late: this arrived at 08:55 and was not written to the ledger at the time.
Recorded now because HR-1739 proposes automated model discovery, and this directive
is the boundary that mechanism must respect.

## Rule

The model the top orchestrator runs on is a **Human-owned setting**. The orchestrator
may not change it — not to save quota, not to escalate for a hard incident, not as a
side effect of a restart or a fallback path. The permitted writers are the Human via
the Telegram `/model` command and the pin in `instance/params.yaml`
(`orchestrator.top_model`, currently `claude-fable-5`) with its source pin in
`orchestrator/launch.sh`.

The second sentence is a design instruction, not just a complaint: **the new
infrastructure must make this structurally impossible**, not merely discouraged.

## Standing violation this names

`instance/params.yaml` already records the drift: the runtime pin reported
`claude_model=claude-fable-5` while the live session ran `claude-sonnet-5`, because
the restart path did not honour the pin. So the current system changes the
orchestrator's model without the Human — by omission rather than by decision, which
is exactly as bad from his side of the screen.

Any v3 supervision design must therefore treat "which model is the orchestrator on"
as observable, pinned, and asserted at startup — a mismatch between the pin and the
live session is a fail-closed startup error, not a silent default.
