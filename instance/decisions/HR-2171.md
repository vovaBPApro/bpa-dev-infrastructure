## What it requires

**Two startup states, both first-class.**

1. **Fresh, zero state.** The installation interrogates the operator: what machine
   is this, what are the key approaches, and it *proposes a strategy fitted to the
   hardware* — how the infrastructure will work, under what rules, with what
   vision. The operator may edit it; **approval is mandatory, editing is not**.
   Then it comes up from nothing. This is the onboarding already specified, and it
   is the same requirement as HR-2120 (the installation must measure the machine
   it lands on and negotiate limits with the installer).
2. **Restore from prior data.** At startup the installation asks whether backup
   files exist. By default it states that it backs up to Google Drive, offers to
   walk the operator through granting access, then locates the files itself —
   because the naming and folder convention is a written rule, so a reader that
   has the rules can find and read them without being told.

**Backup.** Keep writing locally as now; back up to Google Drive **hourly**, into
a folder the installation creates under My Drive. Retain roughly ten versions —
the operator's reasoning is that the files are small enough that frequency and
retention are free.

**Why it matters, in his words**: the server may fall over or disappear; he brings
up a new one, grants it access to the same Drive, and restores through it.

## Measured, so the design rests on numbers

- `/root/.local/state/bpa` — **110 592 bytes** (`state.db`, `state.db-wal`,
  `state.db-shm`).
- `/root/.local/state/bpa-dev-infrastructure` — **1 064 bytes**
  (`evidence/meteorite-latest.md`).

So the operator's assumption is correct: hourly backup with ten retained versions
is roughly a megabyte of Drive per two days. Frequency is not the constraint.

- Secret scan over `state.db` and its WAL using the canonical pattern from
  `gate/land-lib.sh: land_secret_scan()`, each component checked individually:
  **no hits**. This must be re-verified by the implementing lane rather than
  trusted, and it must be re-verified *continuously* — state grows, and the day it
  contains a token is the day an hourly job publishes it.

## The boundary the orchestrator must not blur

The orchestrator's own session has Google Drive tools. **That is not the machine
having access.** A backup that runs through an interactively-authenticated session
dies with the session, is absent in headless and cron runs, and cannot be
reconstructed from the repository — which makes it a host-only mechanism and a
Hard Floor 5 defect, exactly the class this row exists to close.

For the installation to back itself up, it needs **its own credential**, provisioned
by the operator. That is V3-2.10, and secret provisioning is one of the few things
the orchestrator is required to ask for (Hard Rule 14).

Two further constraints on the implementation:

- **Backing up is publishing.** Anything written to Drive leaves this host and may
  be retained or indexed after deletion. The enumeration in V3-2.9 must therefore
  say, per item, whether it is safe to send off-host — not only whether it must
  survive.
- **`state.db` alone is not a backup.** Writes are in flight through a WAL; a
  consistent copy needs sqlite's own backup path or a checkpoint.

### Cadence: every five minutes, not hourly

288 uploads a day of a file this size is not a load worth designing around, and
the operator is right that it is free.

But retention must change with it: **ten versions at a five-minute cadence is
fifty minutes of history**, which would lose a whole working session. The
orchestrator proposed, and the operator has not yet ruled on, a two-tier
retention: the last ten snapshots plus hourly snapshots across a day. Whoever
implements this must state the retention it chose and the window it actually
covers, in time rather than in file count — a count is not a horizon.

### The access correction

The operator believed the orchestrator reaches Drive through a service account.
**It does not.** The access is the Google Drive integration attached to his
claude.ai account — an interactive OAuth connection belonging to this session.
There is no service account on this host and no Drive credential in the
installation.

Consequences for the design, which the implementing lane must respect:

- A service account's files land in **the service account's own Drive**, not in
  the operator's. The folder must be created in his My Drive and **shared with the
  service account's address**, or he will never see the backups he is relying on.
- Service accounts have their own storage quota and are not covered by a personal
  Drive plan. At roughly a megabyte a day this does not bind, but the restore path
  must not assume otherwise.
- The credential is the operator's to create (Hard Rule 14, secret provisioning),
  and it belongs in V3-2.10's runbook: what it is, where it goes, what scope it
  needs, and the command that verifies it. Drive scope should be the narrowest
  that permits writing to one folder — not full-account access.
