## The measured obstacle

v3 does not merely lack this — it **structurally forbids** it.

`core/schema.ts`:

```
createManager(input: { id; missionId; parentId; depth }): void {
  if (input.depth !== 1 || input.parentId !== input.missionId)
    throw new SchemaError("manager parent/depth must be mission/1");

createLane(...):
  if (input.parentId !== input.managerId)
    throw new SchemaError("lane parent must be its manager");
```

So the tree is fixed at mission(0) → manager(1) → lane(2), a lane's parent must be its
manager, and **a lane cannot have lane children**. Under the operator's model a
second-level agent both does work and spawns third-level juniors; today a lane can only
be a leaf. The three levels that exist are not the three levels he is describing.

`instructions/roles.md` also says the manager is optional and does not bound the fleet
("A manager, when used, owns one bounded mission and one terminal rollup. The flat
coder-lane fleet remains bounded by capacity policy, not by a manager"), which matches
his sense that the manager layer was set aside.

And none of it runs: the only mechanism that actually starts an agent session,
`orchestrator/fleet/launch-lane.sh`, exists solely on `v2-deprecated`. Every lane
dispatched on 2026-08-03 was launched from that v2 working tree. Structure without an
executor — the repository's dominant defect shape — at the level of the whole agent
model.

## What this record does not decide

Whether the second level is modelled as today's `manager` row, as a `lane` permitted to
parent lanes, or as something else, is a design decision that needs the operator's
restated model first. Recording the obstacle is not the same as choosing the fix, and
choosing it before he restates the model would repeat exactly the failure this file
exists to correct.

## The orchestrator's assessment, recorded because it was asked for

Asked directly whether this helps or gets in the way (Telegram 1878), the answer given
was that it would get in the way **now**, for a reason grounded in the day's
measurements rather than in preference:

The bottleneck on 2026-08-03 was never the number of lanes. Around fifteen ran without
capacity being the limit. The bottleneck was review rounds and the fact that every
landing is verified by the orchestrator re-executing the acceptance commands at the
landed SHA. A second-level agent that raises juniors necessarily reports a **rollup** of
their work — and a rollup is precisely the thing that cannot be re-executed. Today's
discipline would be replaced by trust in a summary, in a repository whose dominant
defect is correct-looking claims with nothing behind them, and where `V3-0.5` already
records that nothing can force a lane to report honestly in the first place.

The condition under which it becomes worth building: juniors are restricted to work
whose result is **machine-checkable by the level-2 agent** — a test that passes, a
command that exits 0 — so the level-2 agent verifies rather than summarises. Then the
hierarchy is a quota optimisation with a real verification boundary, not an extra floor
between the work and the evidence.

Sequencing that follows from that: V3-1.6 (nothing launches an agent on v3 at all) is
strictly prior — there is no point designing three levels of dispatch on a line that
cannot dispatch one.

A bias worth stating: the flat fleet is what the orchestrator currently operates well,
so "the familiar shape is better" is not a neutral judgement. The operator has been
thinking about this model longer and the decision is his.
