Findings:

1. **Blocking death/duplicate defect:** on acknowledgement timeout `failOrRetry()` immediately returns the row to `ready` without terminating or fencing the previously launched worker. A retry can therefore launch a duplicate while the original worker is alive. The “death without duplicate” test covers only death after the row was changed to `running` and after the worker eventually writes terminal evidence; it does not probe the acknowledged timeout/retry race.
2. **Blocking crash window:** the worker is spawned before its PID/running state is durably saved. A dispatcher death between `Bun.spawn()` and `updateOwned()` leaves the durable row `claimed`; `reconcileRunning()` examines only `running`, so recovery neither reconciles nor safely retries it.
3. **Blocking stale lock:** `locked()` uses a directory lock with no owner identity, expiry, or stale-lock recovery. Dispatcher death while holding it permanently blocks all future state operations after the bounded wait. This contradicts restart reconstruction.
4. **Blocking evidence trust:** terminal JSON is parsed without schema validation and may name any existing `reportPath`; the claimed SHA is only checked for truthiness (the noop fixture even uses `synthetic-1`). The dispatcher can mark `clean` without proving that the report belongs to the attempt, that the SHA is a Git commit/current candidate, or that artifact/report content is authentic.
5. **Blocking contract mismatch / false green:** the implementation uses an independent JSON snapshot instead of `core/schema.ts`, as its own report acknowledges. Therefore “transactional” means only rename under a local directory lock, not the canonical fenced durable transaction. No donor fixture is executed and no red-before evidence is recorded.

Rollback posture: additive and revertible before integration. Runtime directories/workers are not safely reaped by this implementation; rollback after execution would require explicit worker/process and stale-lock cleanup evidence.

Concurrent receivers/flushers in one process can overwrite one another, lose updates, duplicate acknowledgement/send, or collide on the same temp file. 5. **Donor parity/red-before unproven:** no vendored OLD status/mailbox/replay fixture is executed by these locks and no fail-before evidence is recorded. The new tests do not establish parity with the donor contracts named by the plan.

Rollback posture: additive files are revertible before deployment. Once used, inbox/outbox JSON has no version migration/rollback procedure beyond rejecting non-v1 state; preserve runtime files during rollback to avoid losing pending messages.
