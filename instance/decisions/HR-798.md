## Ruling

1. **Data imports (Gmail included) are implemented and executed by the
   PRODUCT** — its own code paths, triggered through its own UI/flows.
   Orchestrator/agents must not run imports directly against product data.
2. **The service account exists for verification only**: agents use it to
   test WHAT THE PRODUCT DID — not to perform the product's work with it.
3. **Acceptance testing happens on the running product via user flow** (login
   → onboarding → fill in → connect integrations), the way it was done on the
   old infrastructure. Stand/runtime evidence for import features means
   walking that flow, not poking the database.
4. UI approval runs in parallel with capability work — a data path without its
   agreed interface is not "done" (ties to PR-10: nothing visual reaches him
   without a consilium first).

Related: W-21 (orphan Gmail tables from an out-of-band migration) is an
instance of exactly the class this ruling forbids. The reconciliation lane's
msg-788 item must judge prior Gmail-sync claims against THIS ruling.
