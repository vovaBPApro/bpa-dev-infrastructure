# HR-1739 — Weekly model discovery and fit-based routing (v3 scope)

Verbatim (Vova, Telegram 1739, 2026-08-03):

> У в3 треба додати механізм який раз на тиждень буде перевіряти які актуальні моделі
> є доступні по кожному провайдеру, що для яких задач кращє пасує, шоб орк завжди
> оюирав серед всіх актуальних моделей, а не оце лайно. Бо регулярно виходять нові
> моделі. Піздніше я може додм щє провайдерів

Raised in direct reply to being told that Spark is unroutable because
`daemon/model-registry.ts` hardcodes four entries (HR-1734). "оце лайно" is that
hardcoded list.

## What v3 must provide

1. **Weekly discovery per provider.** A scheduled mechanism that enumerates the models
   each configured provider currently offers. Not a hand-edited constant — the
   complaint is precisely that new models ship regularly and the list goes stale.
2. **Fit metadata, not just names.** Discovery records what each model is suited to,
   so routing can choose by task fit — cheap mechanical work, design, Tier A review —
   rather than by a hardcoded default. This is the machine-readable form of the
   role-first rule already established in HR-1565 and the cost tiering in HR-1734.
3. **Provider pluggability.** He states he may add providers later. Adding one must be
   configuration plus an adapter, not an edit spread through routing logic.
4. **Selection over the current catalog.** The orchestrator picks from what discovery
   found, so a newly released model becomes available without a code change.

## Boundaries this mechanism must respect

- **HR-1680 — it may not change the orchestrator's own model.** Discovery may inform
  and may surface a recommendation to the Human, but the top orchestrator's model is
  Human-owned. An auto-discovering router that re-points the orchestrator is exactly
  the failure he objected to.
- **Fail-closed, per Hard Floor 7.** If discovery fails or returns nothing, routing
  falls back to the last known-good catalog committed in the repo, and says so. It
  never falls back to "no model", never silently to an account default, and never to
  a model this installation has not verified as runnable — the existing registry
  comment already requires each entry to be verified runnable here.
- **No secrets in the catalog.** Discovery output is committed evidence; provider
  credentials stay out of it (Hard Floor 4).
- **Reproducible from git, per Hard Floor 5.** The discovered catalog and its refresh
  schedule land in the repository. A discovery mechanism that exists only as host
  state repeats the defect found on 2026-08-03, where 8 canonical units were missing
  from the host and nothing noticed.

## Relationship to current work

This is **v3 scope** and does not authorise work on the current host's registry
beyond HR-1734's narrow ask (make Spark routable so paid capacity stops sitting
idle). The weekly discovery mechanism is the general solution that replaces the
hardcoded list; HR-1734 is the stopgap until v3 carries it.
