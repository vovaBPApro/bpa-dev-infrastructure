# HR-292 — product: shared-drive onboarding grants the service account Viewer

**This is the first PRODUCT requirement captured**, not control-plane work. It
arrived while product execution is still gated behind the reliability set
(HR-281), per the orchestrator's own commitment that product CONTEXT is accepted
immediately and stored verbatim while product EXECUTION waits.

## Verbatim (Vova, 2026-07-31, Telegram 292)

> З приводу розшарювання папок.У нас же ж така історія, що ми створюємо shared drive, коли підключаємо Google.Скажи, ти при створенні shared drive можеш додавати service account з правами viewer? Тобто ти ж зрозумів, що я кажу про продукт. Коли ми продукт підключаємо до Google Drive, там даєш сервіс-акаунту права viewer, наприклад.Якщо в тебе є сервіс-акаунт і він налаштований, то даєш. Якщо ні, то просто пропускаєш цей крок.

## The requirement

During the product's Google Drive connection flow, when a **shared drive** is
created:

1. If a service account **is** configured → add it to the shared drive as
   **Viewer**.
2. If it is **not** configured → **skip the step silently**; the connection must
   still complete. This is a conditional enhancement, never a hard dependency.

>

>
> Тільки ж це функціонал уже продукту. Тобто треба, щоб ти це десь записав, щоб коли будеш працювати над продуктом, ти підняв цю інформацію і не загубив.

### Requirement: degrade gracefully, never fail the connection

The shared drive is normally **created fresh at connection time**, so the actor
is usually organizer. But when granting the service account fails for any reason,
the connection must still be treated as SUCCESSFUL, and the user is shown a
message along these lines:

- everything was created correctly — the connection is done;
- the service account could NOT be added automatically;
- you can grant it Viewer on the new shared drive yourself;
- here is the address to add: `<service-account email>`.

So there are three outcomes, not two: granted / not-configured-so-skipped /
attempted-and-failed-so-tell-the-user-how-to-finish-it by hand. The failure path
must surface the account address in the message — a user told "it failed" without
the address cannot act on it.

### Fourth case (Vova, Telegram 299): no service account exists at all

> Ну є те, що четвертий випадок, коли просто нема service account, у тебе нема ключа, і тоді не треба нічого додавати.
>
> Тоді, скоріш за все, це вже в production моді запускається

Distinct from case 2. Case 2 is "the deployment has the concept but this install
has not configured one". Case 4 is that there is **no service account and no key
present at all** — nothing to grant, so the flow does not attempt it and does not
mention it to the user. No message, no error, no residue in the UI.

He expects this to be the normal **production** shape, so it must be the quiet
default rather than an edge case bolted on: the connection flow must read as
complete and untroubled when no service account exists.

Net: four outcomes — granted / configured-but-skipped / attempted-and-failed
(tell the user, with the address) / absent-entirely (say nothing).

## Technical shape (answered to him, 2026-07-31)

Drive API `permissions.create` against the shared drive itself:
`role=reader`, `type=user`, `emailAddress=<service-account>`,
`supportsAllDrives=true`.

Why shared-drive membership rather than per-folder sharing: membership covers the
entire drive including content added later, and survives file-ownership changes.
Per-folder grants decay — they miss new content and break when ownership moves.

Preconditions to design around:
- Granting requires **organizer** rights on that shared drive.
- Google **Workspace** is required for shared drives (not personal Gmail).

## Bearing on the current control-plane need

The same pattern solves today's debugging access: rather than sharing folders
piecemeal with `bpa-dev-orchestrator@bpa-automations.iam.gserviceaccount.com`,
one shared drive with that account as Viewer covers everything placed in it.
