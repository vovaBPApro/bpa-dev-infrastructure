# Parked — V3-1.5 (`meteorite/run.sh`), 2026-08-03

Row V3-1.5 — the infrastructure meteorite, Hard Floor 5's own executable proof —
exhausted the HR-1726 cap of three review rounds without an independent ACCEPT. It is
**parked with evidence**.

This is the most consequential park of the day, so the reasoning is written down rather
than summarised: the row was very close, and "very close" is exactly when a cap is
tempting to ignore.

## Retained artifact

Branch `ag-s3-1-r3`, tip `a7e3b761fad157d196a000633df313a7f7bba696`, pushed to origin so
it survives the loss of this host. Three commits: the runner, the SHA pinning, and the
candidate-proof mechanism. Do not reap it.

## The row was re-scoped before it started, and that stands

The workboard said "port `meteorite/run.sh`". Reading the donor first showed the
instruction was wrong: `v2-deprecated:meteorite/run.sh` is a **product** meteorite that
clones a separate product repository (`PRODUCT_GIT_URL`) and rebuilds *that*. No product
repository exists (`instance/params.yaml: phase = sole-mission`), so a faithful port
could only ever fail on a missing contract — the defect class V3-1.2 was rejected for.

The infrastructure meteorite was never a script at all. It was a hand-run procedure,
executed once, on 2026-07-31, recorded in `v2-deprecated:reports/meteorite-test.md`,
verdict **FAIL**. The re-scope was correct and is not what parked the row.

## What the three rounds proved — this is not a failed row, it is an unfinished one

Confirmed by execution across three independent reviewers:

- **The runner works on the happy path.** The candidate reaches the container through
  credential-free HTTPS and two temporary remote refs — no mount, no volume, no
  `docker cp`, no host networking, no `HOME`, no SSH, no host-environment passthrough.
  The report truthfully labels the source as `temporary tracked-remote refs`, measures
  requested and tested SHA as the same commit, executes every stage, and removes the
  container and both refs.
- Bare invocation and a local source fail before Docker; a SHA mismatch is NO-GO; every
  stage failure flows through `fail`, keeps `result=NO-GO`, names the stage, exits
  non-zero; a signal returns 143 and still tears the container down;
  `METEORITE_KEEP=1` is the only retain path; the three unproven boundaries are literal
  report content; the cheap tests start no container; mutating the verification path
  makes the suite red.
- **Its first real run found real defects.** Against `origin/main` in a clean
  `ubuntu:24.04` it failed closed at the full-suite stage with 17 failures, and the
  reviewer confirmed these were genuine clean-rebuild properties rather than runner
  artifacts: the local-only `v2-deprecated` donor ref (fixed and landed, `787bb40`) and
  the `/usr/local/bin/bun` trust boundary. That is the mechanism doing its job before it
  was finished.

## Why it did not land

Two blocking findings at round 3, both traced to the same place — the temporary refs the
candidate proof publishes:

1. **`meteorite/prove-candidate.sh:52-66,76-79` — cleanup is not crash-safe.** The
   reviewer terminated the wrapper during a real container proof. **Both published refs
   remained on `origin`**, and the wrapper emitted no terminal verdict and no cleanup
   line. Reading explains it: cleanup knows only the array entries appended *after*
   `git push` returns, so a signal delivered between the remote accepting a push and the
   append leaves that ref unknown to the trap. A KILL or host death cannot run the trap
   at all.

2. **`meteorite/prove-candidate.sh:52-64` with `meteorite/run.sh:214-216` — a failed
   cleanup cannot revise the report.** The report is written before publication cleanup
   runs. When deletion fails, the process status changes but the durable report still
   says `result: clean` and `blocker: none`. The new tests cover deletion after runner
   success and failure, but not deletion failure itself.

Finding 2 is the one that makes this fail-closed rather than tidy-up: a retained
artifact reading `result: clean` for a proof that did not fully complete is a false green
in the mechanism whose entire purpose is refusing false greens. Finding 1 is how this
repository accumulated 1372 branches — refs that leak because the only thing deleting
them is a trap on the happy path.

Origin was checked after the review and carries no orphaned meteorite refs; the reviewer
deleted the two it created.

## The lock the recut must satisfy

1. **Orphan refs are reaped by something that does not depend on the publishing process
   surviving.** A trap cannot be the only mechanism, because KILL and host death do not
   run traps. The shape that fits this repository is a sweeper over a reserved namespace
   (a dedicated `refs/` prefix, with the ref name carrying its own creation time), run by
   `hygiene/reap.sh`, which already exists, already has an installer, and already has a
   protected-branch discipline. Publish into a namespace that is safe to sweep, then
   sweep it — do not try to make the trap perfect.
2. **The durable report is written after cleanup, or is revised by it.** A cleanup
   failure must make the report `result: NO-GO` with the leak named. Test deletion
   failure explicitly and assert the report content, not just the exit status.

Red against `a7e3b76`, green at the recut tip.

Each round closed the previous finding and exposed the next one, which is what a review

## Consequence, stated plainly

v3 has **no** executable clean-rebuild proof while this is parked. The claim "the
repository alone can rebuild this host" is therefore unverified on this line — and the
one real run performed today says it is currently **false** (17 failures, two causes,
one already fixed). Nobody should read the absence of a red meteorite as a green one.
