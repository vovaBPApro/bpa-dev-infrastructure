## The row

`bpa-deploy-drift-guard` — the unit whose job is noticing that deployed units drifted
from the tracked set — **was itself among the 8 units missing from the host** on
2026-08-01. The detector was part of what went undetected, for days. So the row was
never "write a drift checker"; it was "make the checker's own absence impossible to
miss".

## Three rounds, one defect, three hiding places

| round | what it did | why it failed |
|---|---|---|
| 1 | made the script the `ExecStart` of the guard service, which checked its own timer | pure circularity — delete the guard and nothing runs, nothing reports |
| 2 | added an independent call edge via `ExecStartPre` on `bpa-meteorite.service.in` | that service was **not armed**, so the witness still never ran |
| 3 | armed it in `bootstrap/install.sh` and locked the arming | the lock **mocks** systemd rather than executing it |

The reviewer's summary is the sentence to remember: *"The circularity has moved from an
unarmed template to an unexecuted mock assertion."*

Round 3's lock (`bootstrap/deployed-drift.test.sh:32-49`) greps the call edge, replaces
`systemctl` with a shell function, invokes `arm_meteorite_witness`, and proves only
that `daemon-reload` and `enable --now bpa-meteorite.timer` were **requested**. It
never runs a disposable systemd manager, never observes the timer trigger the service,
and never observes that service execute `ExecStartPre` while the guard is absent. Its
later `run_check` is a direct fixture call, not a timer/service invocation.

So the new evidence would not catch the original failure — the V3-0.22 test, failed
three times over on one row.

## The witness chain, traced and named

The reviewer wrote it out, and it is the most useful artifact this row produced:

```
operator runs tracked bootstrap/install.sh
  -> installer renders units
  -> systemctl enable --now bpa-meteorite.timer
  -> timer schedules bpa-meteorite.service
  -> service ExecStartPre runs check-deployed-drift.sh
  -> probe checks the drift guard
```

**Nothing independently witnesses deletion or disablement of the meteorite timer after
application.** The chain honestly terminates at the one-time operator application plus
systemd's persisted timer state. That terminator is acceptable — every such chain ends
somewhere — but only if the scheduling edge is *executed* as evidence rather than
asserted.

## The lock the recut must satisfy

An executable **disposable-systemd** proof that (a) applying the installer arms the
tracked timer, and (b) the timer and service actually report guard absence or
disablement. A mock that records intent is what parked this round.
