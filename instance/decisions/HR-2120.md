## The requirement

The bootstrap already brings the repository up on bare hardware (Hard Floor 5, the
meteorite). What it does not do is **fit the installation to the machine**. Every limit in
this repository today is a constant derived from nothing, and those constants would travel
to a machine with different cores, memory and disk and be equally wrong there.

His shape, which is the right one:

1. Bootstrap installs and the human authenticates a provider CLI — that step already
   exists and is unavoidable, because credentials are interactive.
2. **Once a model is reachable, use it**: measure the machine, propose the behaviour —
   fleet size, per-lane cgroup limits, heavy-step concurrency, what runs in tmpfs — and
   explain the reasoning.
3. **Agree it with the human doing the install**, rather than deciding silently. The
   person setting up the machine is the one who knows what else it must do.
4. Write the agreed values into tracked instance config, so the next rebuild of *that*
   machine is reproducible and the next rebuild of a *different* machine re-negotiates.

This is the same principle as HR-2088 applied to hardware instead of model names: the
system discovers a moving external fact rather than being told it once.

## The RAM question, answered honestly

This host has 251 GB of RAM and 12 cores; 4 GB were in use while five lanes ran and the
load average was 16. **Memory is not our scarce resource and will not become one.** The
workload is CPU-bound: test suites, `shellcheck`, container builds, meteorite rebuild
proofs. Whisper and OCR are single-digit gigabytes. Ten parallel product builds would be
tens of gigabytes, not hundreds.

The one use with real return is **converting the abundant resource into the scarce one**:
put lane worktrees and test scratch on tmpfs, so the I/O-heavy suites stop paying disk
latency. That is a genuine speedup of the exact step that is currently the bottleneck, and
it costs memory we are not otherwise using.

The honest conclusion — which the negotiation in this row is meant to produce on any
machine — is that this box is over-provisioned for memory and under-provisioned for cores,
and the fleet size should be derived from cores, not from RAM.
